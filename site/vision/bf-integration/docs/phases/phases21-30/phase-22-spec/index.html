Phase 22: Trading Partner Registration System¶

Goal¶

Allow external trading partners to self‑register, enter a pending queue for admin approval, and upon approval become limited‑access partners capable of sending/receiving documents, with a clear upgrade path to become full BridgeFlow customers.

Issue 22A: Public Partner Registration Portal¶

Assignee: Agent4
Labels: phase:22, frontend, auth, registration

Deliverables¶

  1. Public sign‑up route /partner‑signup
  2. Standalone page, no login required
  3. Form: Partner name, admin email, password, contact info
  4. Backend registration endpoint POST /api/auth/register-partner
  5. Creates:
    • Organization with type = 'partner'
    • User with role = 'partner'
    • PartnerRegistration record with status = 'pending'
  6. Email verification required before activation
  7. Confirmation page after sign‑up
  8. “Thank you for registering. Your account is pending approval.”
  9. Links to support/docs

Guardrails¶

  • One partner per registration
  • Email must be unique across system
  • No automatic activation — admin must approve
  • Reuse existing auth flow (JWT, verification emails)

Issue 22B: Admin Approval Queue & Feature Gating¶

Assignee: Agent4
Labels: phase:22, backend, admin

Deliverables¶

  1. Admin queue UI /admin/partner‑queue
  2. Lists pending registrations (name, email, submitted date)
  3. Actions: Approve / Deny (with reason)
  4. Approval workflow
  5. Approve → creates TradingPartner record linked to inviting SMB’s org (TBD later)
  6. Sets accessLevel = 'limited' on partner’s organization
  7. Sends approval email to partner
  8. Feature gating
  9. accessLevel = 'limited': can only send/receive via existing bridges, no canvas, no bridge creation
  10. accessLevel = 'full': full customer access (future upgrade)
  11. Notifications
  12. Email to partner when approved/denied
  13. In‑app alert to SMB customer when invited partner is approved

Guardrails¶

  • RBAC not used — RLS isolates partner data
  • Pending registrations are visible only to admins
  • Denied registrations are logged but soft‑deleted

Issue 22C: Partner Onboarding & Conversion Path¶

Assignee: Agent4
Labels: phase:22, frontend, onboarding

Deliverables¶

  1. Post‑approval onboarding wizard /partner/onboarding
  2. Steps:
    1. Confirm contact/details
    2. Set up first connection (CSV or QBO)
    3. Generate first API key
    4. View limited dashboard
  3. Limited partner dashboard
  4. Inbox/outbox (documents sent/received)
  5. API key management
  6. No canvas, no bridge configuration
  7. Upgrade path
  8. “Upgrade to full account” button (placeholder for future billing)
  9. If upgraded, accessLevel = 'full' and partner becomes full customer with canvas access

Guardrails¶

  • Onboarding skippable (partner can exit and return)
  • Dashboard only shows data scoped to partner’s own org (RLS)
  • Upgrade button is non‑functional in Phase 22 — logs event for future phase

Implementation constraints & Agent10 directives (must follow)¶

  1. Security model: RLS is the sole gatekeeper
  2. Do NOT use role = 'partner' or accessLevel in application logic to gate data access.
  3. All data queries (documents, connections, API keys) must rely on PostgreSQL RLS policies that use organization.type and organization.id from the JWT context.

  4. accessLevel is UI-only (e.g., hide/disable “Upgrade” button) and must never be used for backend data isolation.

  5. Auth flow: extend existing registration

  6. Do not add a separate registration endpoint.
  7. Extend /api/auth/register to accept type='partner' (query param or request body) and reuse the existing email uniqueness, password hashing, and verification email flow.

  8. Skip SMB profile creation for partners; link the created User to a new Organization { type: 'partner', accessLevel: 'limited' } on approval.

  9. PartnerRegistration lifecycle

  10. On approve: create the Organization (type = 'partner', accessLevel = 'limited'), link the User to this org, and archive/delete the PartnerRegistration record to avoid duplication.

  11. On deny: soft-delete PartnerRegistration and record denial reason/notes.

  12. RLS policy guidance (for Agent10/DB)

  13. Documents, API keys, and connections must be scoped by current_setting('app.current_org_id') and include organization.type = 'partner' where relevant (see implementation notes below).

  14. Do not hard-code RLS in application logic; add SQL CREATE POLICY statements in migrations or DB init scripts.

  15. Go/No-Go

  16. Agent4 may proceed when they confirm they will:
    • Reuse /api/auth/register (type='partner')
    • Not use accessLevel/role in backend queries
    • Add RLS-aware smoke tests and migration for required policies
